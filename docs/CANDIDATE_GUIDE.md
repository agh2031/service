# Candidate Guide — Remote Java Backend Interview

## Objective

You have **30 minutes** to work on a realistic engineering Issue as if you were part of a distributed backend team. We evaluate how you investigate ambiguity, assess risk, reason about concurrency, and communicate progress.

## Working agreement

- Work from your assigned Issue in a branch; do not push directly to `main`.
- **Do not use AI coding assistants, chatbots, or generated answers** during this live segment. IDE navigation and documentation are permitted.
- Use GitHub Issue comments for clarifying questions or short investigation notes.
- Make your assumptions explicit rather than silently inventing requirements.
- You may explain your reasoning aloud, but write enough context that another engineer could continue asynchronously.
- Do not connect this example to real providers or production systems.
- If you cannot finish the implementation, create a draft PR with the design and test plan instead.

## Deliverables

- A concrete failure scenario explaining what happens in the current code.
- A small change, targeted test, or implementation outline justified by the failure scenario.
- A Draft Pull Request with: **Problem / Root cause / Approach / Verification / Risks / Handoff**.
- A response to an interviewer-supplied review question, if received.

## How performance is evaluated

Technical correctness, autonomy, ambiguity handling, asynchronous communication, and ownership. Typing speed and the number of completed lines are not evaluation criteria.
